# Session Summary — 2026-02-17

## Context
Branch: `velocity-MAPush`. Focused on designing and implementing a dual-push balance reward to force both agents to contribute to pushing, preventing freeloading in both homogeneous (2x Go1, light box) and heterogeneous (Go1 + Anymal, heavy box) scenarios.

## Goal
Create a reward signal that registers dual contributions from both agents, so one agent can never slack even if it (or the box) allows solo pushing.

## Design Iteration

### Approach A (IMPLEMENTED, FAILED): Velocity-Toward-Box Balance
**Idea:** Measure each agent's velocity projected onto the agent→box direction. Compute `balance = min(v_push) / max(v_push)` across agents. Gate the velocity tracking reward multiplicatively:
```
vel_track_reward *= alpha + (1 - alpha) * balance
```

**Mass normalization:** Each agent's push velocity scaled by `m_i / M_total` so lighter agents aren't disadvantaged in the balance ratio.

**Result:** `avg_dual_push_balance ≈ 1.6e-4` (essentially zero), dropping to `1.1e-4` at 25M steps. Tracking reward was ~2-2.5x smaller than baseline — meaning the gate was stuck at ~alpha (0.3) constantly.

**Root cause:** The metric measures velocity *toward* the box center. But an agent that is successfully pushing the box is moving *with* it, not toward it. Its velocity is roughly perpendicular or parallel to the agent→box vector. So the dot product is near zero even when the agent is actively pushing. The metric punished good behavior.

**Key insight:** Velocity toward box ≠ pushing contribution. An agent pushing the box moves alongside it with low relative velocity toward the box center.

### Approach B (IMPLEMENTED, CURRENT): Proximity-Gated Velocity Alignment
**Idea:** Instead of velocity toward box, measure how much each agent's velocity aligns with the *box's velocity*. An agent pushing the box moves with it; a freeloader doesn't.

```python
contribution_i = proximity_i * alignment_i * mass_fraction_i

where:
  proximity_i = clamp(1 - (dist_to_box - contact_dist) / contact_dist, 0, 1)
  alignment_i = clamp(dot(agent_vel_i, box_vel_dir), min=0)
  mass_fraction_i = m_i / M_total
  contact_dist = 1.0m  (agents in contact ~0.8-1.0m from box center)

balance = min(contributions) / (max(contributions) + eps)
gate = alpha + (1 - alpha) * balance
vel_track_reward *= gate
```

**Why this should work:**
- Agent pushing box: near box (proximity ≈ 1), moving with box (alignment high) → high contribution
- Freeloader standing still: velocity = 0 → alignment = 0 → contribution = 0 → balance = 0 → gate ≈ alpha
- Freeloader far away: proximity ≈ 0 → contribution = 0 regardless
- Both pushing equally: balance ≈ 1 → gate ≈ 1 → full tracking reward
- Box not moving: alignment is ~0 for everyone, but tracking reward is already ~0 anyway (no velocity match)

**First test result (7M steps):** Contributions were still tiny (~1e-5 to 1e-4), gate stuck at ~7e-4 (effectively alpha again). However, agent1 contribution was ~4x agent0's — real signal showing asymmetric engagement.

**Root cause:** When box speed is near zero (before agents start pushing, between pushes), `box_vel_dir` is computed from a near-zero velocity vector. The alignment dot product becomes noise around zero, clamped to 0 half the time. Since the box is stationary most of the time early in training, the contributions are dominated by these noise-zero steps.

### Fix: Box Speed Threshold (IMPLEMENTED)
Added `box_speed_threshold = 0.1 m/s` — balance is only computed for envs where the box is meaningfully moving. When box speed < 0.1: balance = 1.0 → gate = 1.0 → no penalty. This matches the existing `push_reward` threshold (box_speed > 0.1 triggers push reward), so the balance mechanism activates at the same point the environment considers the box to be "moving."

```python
box_moving = box_speed > box_speed_threshold  # 0.1 m/s
balance = torch.ones(N)  # default: no gating
if box_moving.any():
    # compute balance only for envs where box moves
    ...
    balance[box_moving] = min_c / (max_c + eps)
```

**Status:** Implemented, not yet tested in training.

## Key Architectural Notes

### Why team reward gating (option A) over individualized penalty
We considered three approaches:
- **A) Multiplicative gating on tracking reward** (implemented) — `reward *= alpha + (1-alpha) * balance`
- **B) Additive penalty** — `reward -= penalty * (1 - balance)` — doesn't reduce the base reward signal
- **C) Individualized penalty** — each agent penalized for own low contribution — strongest but breaks team reward structure

Option A was chosen because it directly reduces the dominant reward signal (velocity tracking) when effort is unbalanced. The freeloader can't get the full tracking reward even if the box moves correctly.

**Limitation:** This is still a team reward. Both agents see the same reduced reward. The freeloader doesn't know it's specifically *its* fault. But the signal is that "when I don't push, total reward is low" — with separate actor networks (HAPPO), each agent should learn that its own pushing action correlates with higher reward.

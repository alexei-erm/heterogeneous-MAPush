### OCB Reward Pattern (Observed Across All Runs)
- **0-20M:** OCB rises to plateau (~3e-3) — agents learn "be behind box"
- **20-80M:** Plateau — good positioning, not yet pushing efficiently
- **80M+:** OCB drops to ~5e-4 — agents prioritize pushing over perfect positioning

This is expected: OCB is `cos(θ)` between box-surface normal and box→goal direction. As agents learn to push dynamically, they sacrifice perfect OCB positioning for more productive (messier) pushing behavior.

### Core Problem Identified: Lack of Urgency

Success rate climbs and collaboration is improved, but agents are **slow to engage**. They don't sprint to position behind the box — they meander, eventually get there, and push late in episodes. Compared to vanilla MAPPO with 2×Go1, the heterogeneous team is much less efficient.

**Root cause:** No reward for *speed of engagement*. Current rewards are:
- Position-based (approach, OCB) — satisfied by being near/behind box at any speed
- Event-based (push, goal_push_bonus) — only fire once box moves, no incentive to make it happen sooner
- Success (reach_target) — sparse, doesn't differentiate fast vs slow completion

## Planned Implementation: Approach Velocity Bonus

### Concept

Add a reward for each agent's **velocity toward the box**, not just proximity. An agent standing still at 1.5m gets nothing; an agent running toward the box gets rewarded.

```python
vel_toward_box_i = dot(agent_vel_i, normalize(box_pos - agent_pos_i))
approach_velocity_bonus_i = scale * clamp(vel_toward_box_i, min=0)
```

- Only rewards positive velocity toward box (not away)
- Continuous and dense — gradient available at every step
- Complements existing `approach_reward` (static distance penalty) with a dynamic velocity signal
- Should make agents learn: "run to box quickly" rather than "drift toward box eventually"

### Implementation Plan

#### File: `mqe/envs/wrappers/go1_push_mid_wrapper.py`

**Step 1: Add config parameter**
- Add `approach_velocity_bonus_scale` to reward config (default 0, disabled)
- Read it in wrapper `__init__` alongside other reward scales

**Step 2: Compute per-agent velocity toward box**
In the reward computation section (after approach_reward, ~line 815):

```python
if self.approach_velocity_bonus_scale != 0:
    total_vel_bonus = torch.zeros(self.num_envs, device=self.device)
    for i in range(self.num_agents):
        # Vector from agent to box (2D)
        agent_to_box = box_pos[:, :2] - base_pos[:, i, :2]
        dist = torch.norm(agent_to_box, dim=1, keepdim=True) + 1e-6
        agent_to_box_dir = agent_to_box / dist

        # Agent velocity projected onto agent→box direction
        agent_vel = base_vel[:, i, :2]
        vel_toward_box = torch.sum(agent_vel * agent_to_box_dir, dim=1)

        # Only reward positive velocity (moving toward box), clamp negatives to 0
        vel_toward_box = torch.clamp(vel_toward_box, min=0.0)

        # Optional: decay bonus when already close to box (don't reward running into box)
        # proximity_decay = clamp(dist.squeeze() / contact_threshold, 0, 1)
        # vel_toward_box = vel_toward_box * proximity_decay

        total_vel_bonus += vel_toward_box

    # Team reward (average across agents, like approach_reward)
    if self.mapush_og_rewards_teamified:
        total_vel_bonus = total_vel_bonus / self.num_agents

    approach_vel_reward = self.approach_velocity_bonus_scale * total_vel_bonus

    reward[:, :] += approach_vel_reward.unsqueeze(1).repeat(1, self.num_agents)
    self.reward_buffer["approach_velocity_bonus"] += torch.sum(approach_vel_reward).cpu().item()
```

**Step 3: Add to config**

In `task/cuboid/config.py` or `go1_push_mid_config.py`:
```python
class rewards:
    approach_velocity_bonus_scale = 0.001  # Tune this — start small
```

**Step 4: Add CLI flag** (optional, for easy toggling)

In `HARL/harl_mapush/train.py`:
```python
parser.add_argument("--approach_velocity_bonus_scale", type=float, default=0.0)
```

Pass through `mapush_env.py` → `utils.py` → config.

#### Design Decisions

- **Team reward** (averaged, broadcast to both agents) — consistent with current structure
- **Not gated by contact-force gate** — this is a positioning/approach reward, not a pushing reward. We want both agents to rush to the box regardless of who's pushing.
- **Optional proximity decay** — can reduce bonus when agent is already close (within contact_threshold). Without it, an agent running at the box from 0.3m away still gets rewarded, which is fine but less useful. Start without decay, add if needed.
- **Scale suggestion:** Start at 0.001. Go1 walks at ~0.5 m/s, so max contribution per agent per step ≈ 0.0005. Should be noticeable but not dominate other rewards.

## Monitoring Contact-Force Gate Effect

### Current Metrics
- `avg_dual_push_balance` — raw balance ratio (0=one idle, 1=balanced)
- `avg_dual_push_gate` — the multiplier applied to rewards (alpha to 1.0)

### Problem
These are averages across 500 envs and all steps. Can't tell when the gate is active vs inactive, or how much reward is being suppressed.

### Proposed Additional Metrics

Add these to the contact-force gating section (~line 674):

```python
if self.contact_force_gating:
    cf_balance, cf_contributions = self._compute_dual_push_balance()
    cf_gate = self.contact_force_gating_alpha + (1.0 - self.contact_force_gating_alpha) * cf_balance

    # Existing metrics
    self.reward_buffer["avg_dual_push_balance"] += cf_balance.mean().item()
    self.reward_buffer["avg_dual_push_gate"] += cf_gate.mean().item()
    for i in range(self.num_agents):
        self.reward_buffer[f"avg_push_contribution_agent{i}"] += cf_contributions[:, i].mean().item()

    # NEW: Gate activation analysis
    # 1. Fraction of envs where gate is "fully active" (near alpha, i.e. one agent idle)
    gate_near_min = (cf_gate < (self.contact_force_gating_alpha + 0.1)).float().mean().item()
    self.reward_buffer["gate_near_min_frac"] += gate_near_min

    # 2. Fraction of envs where gate is "fully open" (near 1.0, balanced pushing)
    gate_near_max = (cf_gate > 0.9).float().mean().item()
    self.reward_buffer["gate_near_max_frac"] += gate_near_max

    # 3. Fraction of envs where gate actually fires (someone pushing, balance < 1)
    gate_active = (cf_gate < 0.99).float().mean().item()
    self.reward_buffer["gate_active_frac"] += gate_active
```

These give you in tensorboard:
| Metric | What it shows | Ideal |
|--------|--------------|-------|
| `gate_near_min_frac` | % of envs where gate is at minimum (≤ alpha+0.1) — freeloader detected | → 0 over training |
| `gate_near_max_frac` | % of envs where gate is near 1.0 — balanced pushing | → 1 over training |
| `gate_active_frac` | % of envs where gate fires at all (someone pushing but unbalanced) | Informational — shows how often gating matters |

Example interpretation:
- `gate_near_min_frac = 0.4` → 40% of envs have severe freeloading at this step
- `gate_near_max_frac = 0.3` → 30% of envs have balanced pushing
- `gate_active_frac = 0.7` → 70% of envs have someone pushing (other 30% box is stationary)

## Bug Found: Gating Flag Disconnect (CRITICAL)

### Root Cause
The velocity wrapper (`go1_push_vel_wrapper.py`) used a completely different variable for contact-force gating than the mid wrapper:

- **Mid wrapper**: reads `cfg.rewards.contact_force_gating` (bool) and `cfg.rewards.contact_force_gating_alpha` (float) — set by `--contact_force_gating` and `--contact_force_gating_alpha` CLI flags
- **Velocity wrapper**: read `cfg.rewards.dual_push_balance_alpha` — hardcoded to `0.3` in the config class, **ignoring both CLI flags entirely**

So running `--contact_force_gating True --contact_force_gating_alpha 0.1` on the velocity task silently used alpha=0.3 from the config, not 0.1 from the flag. The `--contact_force_gating True` flag also had no effect — gating was always on (whenever `dual_push_balance_alpha < 1.0`).

### Fix
Replaced `dual_push_alpha` / `dual_push_balance_alpha` in the velocity wrapper with `contact_force_gating` / `contact_force_gating_alpha`, matching the mid wrapper's pattern exactly. Removed the dead `dual_push_balance_alpha` config variable.

## Reward Landscape Analysis

Analyzed the full reward computation for the latest velocity run:
```
--task go1push_vel --box_mass_range 4 30 --contact_force_gating True
--contact_force_gating_alpha 0.1 --agent0 go1 --agent1 anymal_c --vel_tracking_sharpness 4
```

### Problem: Tracking reward wasn't dominant enough
Before changes, auxiliary rewards (OCB + push) summed to ~55% of the max tracking reward. Agents could earn significant reward just by being positioned well and making the box move in **any** direction, not necessarily the commanded one. The `push_reward` (0.0015) fired whenever `box_speed > 0.1` regardless of direction.

### Decision: Make tracking reward overwhelmingly dominant

| Reward | Old Scale | New Scale | Rationale |
|--------|-----------|-----------|-----------|
| velocity_tracking | 0.01 | **0.1** | 10x increase — now ~15-20x larger than any auxiliary term |
| push_reward | 0.0015 | **0.0** | Disabled — rewarded any-direction movement, diluting directional signal |
| angular_vel_penalty | -0.005 | -0.005 | Unchanged — cooperation signal |
| velocity_ocb | 0.004 | 0.004 | Unchanged — now only 4% of max tracking |
| approach | 0.00075 | 0.00075 | Unchanged — now only ~1% of max tracking |
| collision | -0.001 | -0.001 | Unchanged |
| exception | -5 | -5 | Unchanged |

### cos^n Sharpness Decision: Keep cos^4

Considered cos^8 for sharper precision. Analysis:

| Direction error | cos^4 | cos^8 |
|-----------------|-------|-------|
| 0° (perfect) | 1.0 | 1.0 |
| 20° | 0.779 | 0.607 |
| 30° | 0.563 | 0.317 |
| 45° | 0.250 | 0.063 |
| 60° | 0.063 | 0.004 |

**Kept cos^4**: With tracking at 0.1, the difference between 30° and 0° is already `0.1 * (1-0.563) = 0.044` per step — a massive gradient. cos^8 would risk being too sparse early in training when agents are learning to approach and push roughly correctly (30-60° off). cos^4 gives meaningful gradient at those angles to improve from.

## Contact-Force Gating Recap (for decision-making)

### Mechanism
```
For each agent i:
    raw_force_i = sum |horizontal contact force| on non-foot bodies
    contribution_i = raw_force_i / agent_mass_i    (N/kg, mass-normalized)

balance = min(contributions) / max(contributions)   [0, 1]
gate = alpha + (1 - alpha) * balance                [alpha, 1.0]

velocity_tracking_reward *= gate
```
Activates only when `box_speed > 0.01 m/s`.

### Prior results on velocity task (sessions 2026-02-25, 2026-03-12)
- alpha=0.1: Agents glued to box, optimized "maintain contact" over "push effectively"
- alpha=0.5: No coordination effect
- alpha=0.3: Intermediate — still pathological on velocity task
- **Conclusion was**: gating doesn't suit velocity task well

### What's different now
- Tracking reward is 10x stronger (0.1 vs 0.01) — may overpower the "maintain contact" trap
- Push reward disabled — no reward for directionless movement
- The flag actually works now (was silently using alpha=0.3 before)

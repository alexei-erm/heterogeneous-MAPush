# Session Summary — 2026-02-25

## Context
Branch: `velocity-MAPush`. Heterogeneous setup: agent0 = Go1 (12kg), agent1 = Anymal (50kg). Focused on implementing and iterating a contact-force-based dual-push balance reward to combat freeloading, plus environment changes (direction-only tracking reward, bigger box).

## Background: Freeloading Problem
In heterogeneous velocity-MAPush, the weaker agent (Go1) learns to stop pushing while the stronger agent (Anymal) does all the work. The team reward structure means Go1 gets rewarded even when idle, and its contribution barely changes the outcome — so it freeloads.

Previous session (2026-02-17) tried two proxy-based balance mechanisms:
- **Velocity-toward-box**: Failed — pushing agents move *with* the box, not toward it
- **Proximity-gated velocity alignment**: Better signal but noisy when box stationary

This session replaced the proxy with **direct contact force measurement** from Isaac Gym's `net_contact_force_tensor`.

## Iteration 1: Contact-Force Balance (Baseline)

**Run:** `results/mapush/go1push_vel/happo/velocity_happo_anymal_dualpushgate_contact/seed-00001-2026-02-25-13-07-16`

### Setup
- Velocity tracking reward: `scale * cos_sim * exp(-speed_error)` (direction + speed magnitude)
- Box: 1.2m × 1.2m × 0.5m (SmallBox.urdf), mass override 8kg
- Spawn radius: r=[1.2, 1.3]
- `dual_push_balance_alpha = 0.3`
- `push_force_threshold = 5.0` N

### Contact-Force Balance Implementation
Replaced the proxy-based `_compute_dual_push_balance()` with direct Isaac Gym contact force reading:

```python
def _compute_dual_push_balance(self):
    contact_forces = self.env.contact_forces  # (num_envs, total_bodies, 3)
    for each agent i:
        # Get non-foot body indices (exclude feet — always touching ground)
        body_indices = agent_body_offset + non_foot_body_indices
        agent_contact = contact_forces[:, body_indices, :]
        # Horizontal force magnitude (XY only, ignore vertical ground normal)
        horiz_force = norm(agent_contact[:, :, :2], dim=2)
        push_force_i = horiz_force.sum(dim=1)  # total per env
        contributions[:, i] = push_force_i * (agent_mass_i / total_mass)

    balance = min(contributions) / (max(contributions) + eps)
    # Only gate when max force > threshold (someone is actually pushing)
    balance[max_c <= threshold] = 1.0  # no gating when nobody pushing
    return balance, contributions
```

**Key design decisions:**
- Non-foot bodies only (base, hips, thighs, calves) — feet always have ground contact forces
- Horizontal (XY) forces only — vertical Z is dominated by gravity/ground normal
- Mass-normalized: `contribution_i = force_i * (m_i / M_total)` — heavier robot's force weighted proportionally more
- Threshold gate: balance only computed when `max(contributions) > 5.0N` — avoids noise when nobody is pushing

**Body layout in contact_forces tensor:**
```
[agent0_bodies(0-16), agent1_bodies(17-33), box(34), target(35)]
Go1: 17 bodies, feet at indices [4, 8, 12, 16]
```

### Results (~60M steps)
- `avg_push_contribution_agent0` (Go1): 0.0035
- `avg_push_contribution_agent1` (Anymal): 0.035
- **10x asymmetry** — clear freeloading by Go1
- Gate was NOT firing: threshold 5.0N too high for mass-normalized average contributions
- All other rewards healthy (push reward, velocity tracking, etc.) — box IS being pushed

**Key insight from user:** Contribution values ~0.003 seem tiny but are averaged across 500 envs. Most envs have zero contact at any given step. The per-env values when pushing are much higher.

## Iteration 2: Lowered Force Threshold (Worst Performance)

**Run:** `results/mapush/go1push_vel/happo/velocity_happo_anymal_dualpushgate_contact/seed-00001-2026-02-26-02-11-18`

### Change
- `push_force_threshold`: 5.0 → 0.01 N

### Rationale
The 5.0N threshold was too high for mass-normalized contributions, so the balance gate never activated despite the 10x asymmetry. Lowering to 0.01N should make the gate fire whenever any meaningful contact exists.

### Results
- **Go1 pushed even LESS than Iteration 1**
- `avg_push_contribution_agent0`: dropped to ~5e-4 (was 0.0035)
- `avg_dist_to_box_agent0`: increased (Go1 moved farther from box)
- Anymal contribution stayed at ~0.038

### Analysis
The lower threshold made the gate fire constantly (even on noise), chronically suppressing the tracking reward. Since Go1 was already struggling to contribute, the additional reward suppression made it give up entirely. The gate punished the team whenever Go1 didn't push — but Go1 couldn't improve fast enough, so it learned to stay away.

**Root cause identified by user:** The `exp(-speed_error)` term in the velocity tracking reward is the real problem. The heterogeneous team (Go1 12kg + Anymal 50kg) physically cannot reach the commanded speed (0.5 m/s). So `speed_error` stays high regardless of Go1's contribution → the tracking reward is uniformly suppressed → Go1 has no gradient to learn from.

## Iteration 3: Direction-Only Reward + Reverted Threshold

**Run:** `results/mapush/go1push_vel/happo/velocity_happo_anymal_dualpushgate_contact/seed-00001-2026-02-28-00-51-04`

### Changes
1. **Removed speed magnitude from velocity tracking reward:**
   ```python
   # BEFORE (Iterations 1-2):
   vel_track_reward = scale * cos_sim * exp(-speed_error)

   # AFTER (Iteration 3):
   vel_track_reward = scale * cos_sim
   ```
   `speed_error` still computed and logged for monitoring, just not used in reward.

2. **Reverted force threshold:** 0.01 → 5.0 N (back to Iteration 1 value)

### Rationale
- **Direction-only reward:** Removes the uniform suppression that made Go1 give up. Now any contribution to pushing the box in the right direction is rewarded, regardless of speed. The weaker agent always has gradient to improve.
- **Threshold revert:** The low threshold caused chronic gating from noise. Back to 5.0N, the gate rarely fires — the direction-only reward change is the main intervention.

### Status
Implemented, ready for training.

4. **Fixed spawn radius** for larger box:
   ```python
   class domain_rand(Go1PushMidCfg.domain_rand):
       init_base_pos_range = dict(
           r=[1.5, 1.6],   # was [1.2, 1.3] — increased for 0.9m box edge (was 0.6m)
   ```

### Rationale
Bigger box provides more surface area for both agents to push from different positions. With the original 1.2m box, agents were crowded and could interfere with each other. The 1.8m box gives more room for complementary positioning.

## Open Questions
1. The 5.0N threshold likely means the balance gate still doesn't fire (mass-normalized values are much smaller). The direction-only reward is the main anti-freeloading intervention. If Go1 still freeloads with direction-only reward, the threshold needs revisiting.
2. The bigger box may help by giving more surface area, but it's also heavier to push (same 8kg mass, but more air resistance / contact area with ground). May need mass adjustment.
3. Contact-force balance measures non-foot bodies only. Go1 pushes primarily with front feet pressed against the box — these forces are excluded. Consider including foot-to-box forces (would need to separate foot-ground from foot-box contact, which net_contact_force cannot do directly).
